* Aim and intended use

- Question :: How well do pinned releases of Kev 0.8B, Kev 4B, and Laya reproduce the owner's personal email Triage Action and Reply Requirement decisions on a frozen sample from the Target Inbox Population?
- Intended use :: Produce a transparent personal case study, decide whether any model merits more data collection or fine-tuning, and decide whether the Simulated Action Policy provides enough evidence to consider a separate limited automation trial.
- Audience :: Technically literate readers who may be new to typed-decision models, probability scoring, selective prediction, and small-sample evaluation.
- Population :: Eligible inbound Gmail messages received from 1 January 2026 00:00 Europe/Berlin through a recorded extraction freeze time in 2026. Include newsletters, receipts, notifications, and personal mail regardless of current read or archive state. Exclude spam, trash, drafts, sent mail, and messages from any of the owner's aliases.
- Decision informed :: Continue experimenting, collect more labels, fine-tune a model, abandon the approach, or design a separately reviewed limited automation trial.
- This analysis cannot support :: Claims about other users, other inboxes, future distribution shifts, production safety, autonomous deletion, general benchmark superiority, or target-domain probability calibration beyond what the small descriptive sample shows.

* Risk tier

- Reason :: The work processes sensitive personal email, creates cloud infrastructure, configures a live Gmail client, and supports a public blog post. The evaluation itself is read-only and must never mutate Gmail.

** Eligibility, census, and sampling

1. Record retrieval start, retrieval end, freeze time, account alias list location, selected Maildir folders, tool versions, and configuration hashes in the Private Manifest.
2. Build two independent eligible-message censuses: one through mu and one by parsing Maildir headers. The second path must not import selection results from the first.
3. Reconstruct thread membership with Gmail identifiers when available and a documented conservative fallback when they are absent. At most one Evaluated Email, the latest eligible inbound message, may represent a thread.
4. Reconstruct only evidence available at the selected message's arrival. Exclude later replies, later messages, and current mailbox actions that reveal the eventual decision.
5. Assign each eligible thread an opaque Evaluation ID and a keyed-hash Sampling Order. Keep the secret key and source mapping private. Freeze the first 200 selected records after eligibility review and before any model prediction is inspected.

Expand to the first 300 records when either task has fewer than 20 examples of any outcome at 200. ** Canonical Email State

The canonicaliser must be deterministic and independent of the model adapter:

- Prefer =text/plain=; otherwise convert sanitised HTML to text.
- Never fetch remote images, tracking pixels, linked pages, or attachments.
- Remove repeated quoted text and signatures under documented rules while preserving the original raw bytes privately.
- Include approved, normalised metadata, the current inbound message, and as much recent earlier thread text as fits every model.
- Use one predeclared head-tail truncation rule when the current message alone is too long. Record every truncation and model-specific token count. No adapter may silently truncate.
- Produce raw-message, canonical-state, and request hashes in the Private Manifest. Every model must receive byte-identical canonical state for the primary comparison; only its serialisation envelope may differ.
- Mark encrypted, corrupt, or attachment-only content as Unsupported Input when the text conversion lacks the evidence required for either task.

** Reference Decision table

The tracked Org table contains one row per Evaluation ID and these non-sensitive columns:

| Column | Allowed value or meaning |
|--------+--------------------------|
| Evaluation ID | Opaque stable identifier |
| Included | =yes= or a declared exclusion reason |
| Triage Action | =keep unread=, =mark read=, =archive=, or =uncertain= |
| Reply Requirement | =yes=, =no=, or =uncertain= |
| Triage uncertainty note | Non-sensitive rubric reason code only |
| Reply uncertainty note | Non-sensitive rubric reason code only |
| Unsupported Input | =yes/no= plus reason code |
| Repeat-labelling stratum | =selected/not selected=, assigned before first labels are exposed for review |
| Repeat Triage Action | Hidden until the repeat pass is complete |
| Repeat Reply Requirement | Hidden until the repeat pass is complete |
| Adjudication state | =not needed=, =resolved=, or =persistently uncertain= |

The owner labels before any prediction is run or inspected. Blindly repeat-label a fixed 20% after at least seven days. Calculate exact agreement separately for Triage Action and Reply Requirement; require at least 90% for each. If either fails, refine the written rubric without looking at model results and relabel the complete selected set. Persistently Uncertain Decisions remain in the population, are excluded from reference-dependent primary scoring for that task, reduce labellable coverage, and enter a sensitivity analysis using each plausible label.

* Method and assumptions

- Method class :: Paired, descriptive, retrospective evaluation of three fixed typed-decision models on one personal inbox, with a predeclared selective-action simulation.
- Method :: Every supported Evaluated Email is scored by every pinned model on the two tasks. Primary probability scores and paired differences are calculated on the same task-evaluable records. Robustness variants test option order, question packing, repeated requests, and probability rounding without changing the primary canonical request.
- Assumptions :: The keyed-hash sample adequately represents the defined Target Inbox Population; one email per thread removes the largest dependence; Reference Decisions are stable enough after the repeat-label gate; frozen model revisions and shipped temperatures represent the products being compared; and the canonical text preserves information material to the two decisions.
- Limits :: A personal retrospective sample is not a general benchmark. Small or rare classes remain imprecise. Current mailbox contents may not perfectly reconstruct arrival-time knowledge. Reliability diagrams are descriptive. Shipped probabilities are not proven calibrated for personal email. The cloud endpoint is IAM access-controlled, not network-private.

** Stable question definitions

- Triage Action :: A three-option =choice= question in the canonical primary order: =keep unread=, =mark read=, =archive=. Keep unread makes no change. Mark read clears unread and retains INBOX. Archive clears unread and removes INBOX while retaining the message in Gmail.
- Reply Requirement :: A binary =noul= question asking whether the owner needs to send a reply.
- Primary request :: Ask both questions in one packed request using the models' shipped temperatures and deterministic evaluation mode. Do not inject date facts, fine-tune, recalibrate, or select thresholds on these evaluation labels.

** Models and adapter boundary

Implement one narrow =ModelAdapter= interface that accepts a Canonical Email State and typed questions and returns a normalised result containing the complete probability distribution, selected answer, model and base revisions, shipped temperature metadata, request hash, elapsed time, and a structured failure. It hides local versus HTTP execution and model-specific serialisation.

- Kev 0.8B :: Run locally on the MacBook. Pin the exact Hugging Face model revision, Qwen base revision, Kev source revision, dependencies, and artefact hashes before predictions.
- Kev 4B :: Run only through the agreed GCP wrapper. Pin the same categories in the baked image.
- Laya :: Run locally on the MacBook. Pin the exact =convaiinnovations/laya-typed-decisions= revision, ModernBERT base revision, Laya source revision, dependencies, and artefact hashes.

Laya belongs in the experiment because it exposes the same semantic question families and full distributions, not because its published benchmark number is directly comparable to Kev. See [[file:../findings/laya-typed-decisions.md][the Laya inquiry]].

The adapter layer must validate option identity, ordering, distribution length, finite values, range, and sum. Kev's two-decimal API probabilities may be renormalised only when rounding makes their sum differ from one; preserve both received and normalised values. Run a Laya sensitivity view after rounding its probabilities to two decimals and applying the same renormalisation.

** Primary and secondary metrics

Compute each task separately. Never compare the numerical Brier value of the three-class task with the binary task.

1. Primary Triage Action score: for each email, sum squared differences between the three predicted probabilities and the one-hot Reference Decision; report the mean.
2. Primary Reply Requirement score: square the difference between the predicted probability of =yes= and the binary Reference Decision; report the mean.
3. For each task and model pair, report the paired difference in per-email Brier contributions. Lower Brier is better.
4. Resample whole Evaluated Emails with replacement 10,000 times using one recorded seed. Preserve all model and task results within an email. Construct simultaneous 95% intervals for the three pairwise Brier differences within each task from the bootstrap distribution of the maximum absolute centred pairwise deviation. Show the point estimate and interval, not only a significance label.
5. Secondary views: accuracy, macro F1, per-class precision and recall, confusion matrices, and mean log loss. Clip probabilities for logarithms only at a declared machine-safe epsilon and report it.
6. Report Wilson 95% intervals for individual rates. Reliability diagrams are descriptive: use at most five equal-count bins with at least 20 observations per bin; reduce the bin count or omit the plot when that rule cannot be met. Display bin counts and uncertainty.
7. Baselines: a leave-one-out class-frequency probability baseline, a majority-class decision baseline, and an always-defer policy with zero automated Coverage. The leave-one-out calculation for each row uses Reference Decisions from all other task-evaluable rows only.
8. Declare a clear leader for a task only when its simultaneous paired Brier interval excludes zero in its favour against each competitor and its observed High-Cost Error rate is no higher on the same evaluable set. Otherwise call the result tied or unresolved. Also report uncertainty for High-Cost Error differences; do not convert “not detectably worse” into proof of equivalence.

** Simulated Action Policy

This policy changes no mailbox state. Apply it to frozen probability outputs:

- Accept =archive= only when its Triage Action probability is at least 0.99 and the Reply Requirement probability for =yes= is at most 0.05.
- Accept =mark read= only when its Triage Action probability is at least 0.95 and the Reply Requirement probability for =yes= is at most 0.05.
- Defer in all other cases, including unsupported input, failed inference, invalid probabilities, or a selected =keep unread= action.

A High-Cost Error is clearing an email whose Triage Action is =keep unread= or returning no-reply when Reply Requirement is =yes=. Report Accepted Set size, end-to-end Coverage, observed High-Cost Errors, and the exact one-sided 95% binomial upper bound for the High-Cost Error rate. A future limited automation trial merits separate consideration only when the Accepted Set contains zero observed High-Cost Errors and that upper bound is at most 5%. With zero errors this requires approximately 59 accepted cases; compute the exact value rather than relying on the approximation.

** Robustness checks

- Evaluate all six permutations of the three Triage Action options for every email and model. The declared canonical order remains primary.
- Compare the packed two-question request with separate requests for the two questions.
- Repeat an identical request and compare returned distributions and selected actions.
- Apply the agreed two-decimal Laya sensitivity transformation.
- For each check report winner changes, maximum absolute probability drift, Simulated Action Policy flips, validation failures, and affected counts. Do not average variants into the primary score.

** System measurements

Measure cold model load/start, warm request latency p50 and p95, total elapsed time, throughput, failure counts, and peak local memory. Separate local and cloud measurements. For GCP report service active time, estimated cost using contemporaneous pricing, and billed cost when available. Do not present an estimate as an observed bill.

** Execution ordering and result cache

1. Freeze and hash the complete request set before model inference.
2. Run Laya locally, unload it, then run Kev 0.8B locally. Do not load both models concurrently on the 8 GB MacBook.
3. Pass the GCP synthetic gate, then run Kev 4B.
4. Join results only by Evaluation ID and request hash. Refuse missing, duplicate, or mismatched rows.
5. Cache private results by exact model revision plus request hash. Reuse only exact matches.
6. Retry a transport failure once and record both attempts. Never silently retry validation or model failures with changed input.
